# ADR 0003: SQLAlchemy 2.0 for data access, Alembic from the first commit

- **Status:** Accepted
- **Date:** 2026-10-24
- **Supersedes:** —

## Context

PS needs a data access layer over PostgreSQL and a way to evolve the schema
without destroying data.

Raw SQL via `asyncpg` was a serious candidate, because one of this project's
stated purposes is to improve the developer's Python and backend skills, and
raw SQL teaches SQL more directly than an ORM does.

Schema evolution is not optional. The schema will change dozens of times during
development, each time against a database holding imported statements that are
tedious to recreate. More importantly, self-deploying users will upgrade
versions against a database containing their own financial history; telling them
to recreate it is not an acceptable upgrade path.

## Decision

SQLAlchemy 2.0 in async mode as the data access layer, with Alembic for schema
migrations, set up before the first table exists.

## Consequences

- A typed query API that works with strict type checking.
- The combination used by most production Python codebases, so the experience
  transfers.
- Schema changes preserve data, in development and on user upgrades.
  `alembic upgrade head` becomes the entire upgrade path.
- An abstraction sits between the developer and the SQL, which slightly dilutes
  the SQL learning. Mitigated by reading the emitted SQL during development.
- Autogenerated migrations must be reviewed before being applied. Alembic's
  autogenerate reports a column rename as a drop plus an add, which silently
  destroys that column's data if run unread.

## Alternatives considered

**Raw SQL via asyncpg.** Teaches SQL better, but hand-rolled row mapping and
hand-written migration scripts are a large amount of work that teaches less per
hour than the application itself does.

**Adding Alembic later, once the schema settles.** Rejected. Retrofitting onto a
populated database requires baselining with `alembic stamp` and is easy to get
subtly wrong. Starting from an empty database makes the first migration a plain
"create everything" and keeps the chain clean.
